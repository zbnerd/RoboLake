# RoboLake M1 Performance Baseline

- **Measured:** 2026-07-13T02:30:09Z
- **Source commit:** `9b5d06ac63940e5f871cd83a9128007735f9ed1a`
- **Harness mode:** `quick`
- **Run ID:** `release-20260713b`
- **Raw JSON SHA-256:** `d0f156e9174feed21c27f3b5effc8ff596f5cdf46b7a7f55ebfbf968b9b58be7`

This is a reproducible local-development baseline, not a capacity promise. It records one run on one
machine with local loopback networking and shared Docker resources. It does not claim WAN, NAS,
cloud S3, concurrency, or M1-limit performance.

## Reproduce

Start from a clean checkout with Docker running:

```bash
ROBOLAKE_BENCHMARK_RUN_ID=release-20260713b \
ROBOLAKE_BENCHMARK_OUTPUT=/tmp/robolake-m1-quick-release-20260713b.json \
scripts/benchmark-m1.sh quick
```

Use a new lowercase run ID when the same object store already contains this run's data. The run ID
salts generated bytes and Dataset names so first-push metrics are not accidentally satisfied by an
older Blob.

The explicit manual large-file profile is:

```bash
ROBOLAKE_MANUAL_LARGE_BYTES=4000000000 scripts/benchmark-m1.sh manual-large
```

It is not part of normal CI. The quick single-large profile uses 64 MiB; a separate 4 GB manual
validation from this release gate is recorded below.

## Dataset generation

`scripts/benchmark_m1.py` creates opaque regular files in bounded 1 MiB chunks. Each unique file is
generated by a deterministic Python PRNG seeded with the run ID, profile name, and unique-file
ordinal. Duplicate paths are independent regular-file copies of one generated payload. Generation
time is excluded from scan/push/pull measurements.

| Profile | Shape | Duplicate content | Logical | Unique content |

## Scan and manifest measurements

`scan` measures the production safe traversal, hashing, and its normal manifest build together.
`manifest build` is a separate replay over the scanned entries. Effective hashing throughput is
logical MiB divided by total scan duration, so it includes filesystem traversal and manifest work;
it is not a pure SHA-256 microbenchmark.

| Profile | Scan ms | Manifest build ms | Effective MiB/s |

Measured operation time across all profiles was 136.697 seconds. The process high-water RSS was
56.043 MiB. RSS is monotonic for the one benchmark process and is not a per-operation allocation
measurement.

The many-small-files profile exposes M1's deliberate sequential control-plane cost: first push uses
three Blob-level control requests plus registration/finalization, while pull issues one capability
per logical entry. This is measured behavior, not a correctness failure.

## Invocation outcomes and resume

Every normal first push created exactly the profile's unique Blob count. Every identical re-push
created zero and reused the complete unique content set.

The interrupted profile stopped before its second PUT:

- interrupted invocation: 1 Blob / 2 MiB created in 0.323 seconds;
- resumed invocation: 3 Blobs / 6 MiB created and 1 Blob / 2 MiB reused in 0.691 seconds;
- combined resolved content: 4 Blobs / 8 MiB, matching the immutable Version.

`created_blob_bytes` is the logical size of objects newly created by that invocation. It is not wire
bytes. The harness does not measure request-body bytes transmitted before provider conflicts,
retries, TCP/TLS overhead, or storage replication.

## Optional manual 4 GB validation

The release gate first confirmed 308,553,060,352 bytes of free space on the shared source,
Docker-data, and temporary filesystem, 15,658,995,712 bytes of available memory, and an unlimited
file-size ulimit. The expected peak disk use was approximately 12 GB: 4 GB source, 4 GB stored Blob,
and 4 GB restored output. The generator and transfer paths use bounded chunks.

The exact command was:

```bash
ROBOLAKE_BENCHMARK_RUN_ID=release-20260713-manual4gb \
ROBOLAKE_BENCHMARK_OUTPUT=/tmp/robolake-m1-manual-release-20260713-manual4gb.json \
ROBOLAKE_MANUAL_LARGE_BYTES=4000000000 \
scripts/benchmark-m1.sh manual-large
```

- **Raw JSON SHA-256:** `ab291679ab886b9809731e3e224692ca179552d1487b8d9b185928543cab3edb`
- **Scan/hash:** 3.707 seconds, 1,029.17 effective MiB/s
- **First push:** 58.948 seconds; one 4,000,000,000-byte Blob created; READY confirmed
- **Identical re-push:** 6.605 seconds; zero created and one 4,000,000,000-byte Blob reused
- **Pull:** 60.059 seconds; one file / 4,000,000,000 bytes materialized
- **Measured operation total:** 125.611 seconds; generation and Compose startup excluded

Pull streamed SHA-256 verification against the source-derived manifest before atomic publication,
proving the restored bytes matched the registered file. The benchmark JSON and API/MinIO logs
contained no presigned URL, capability query, or credential material. This is one local-loopback run,
not a near-limit capacity claim.

## Measurement limitations

- One run per profile; no confidence intervals, warmup policy, CPU pinning, cache drop, or background
  load isolation.
- Local Docker networking and local storage only; no NAS or remote S3 latency/bandwidth.
- Dataset generation and Compose startup are excluded from operation timing.
- Scan time includes traversal, hashing, and production manifest creation; the reported manifest
  time is a separate replay.
- Peak RSS is a process high-water mark accumulated across the run.
- Database query count is not measured. Accurate DB counts would require instrumentation inside the
  API process; the harness records control-plane HTTP request count instead.
- No exact wire-byte metric is collected.
- The 4 GB profile ran once; near-5 GB behavior must not be inferred from that result.
- No concurrent clients, provider replacement, power-loss, or long-duration stability measurement.

These results establish a reproducible M1 comparison point. Any future benchmark should preserve
the JSON metric meanings and report environmental differences rather than comparing unlike runs.
